New project `Z:\src\adaptive-tv\` — the "universal TV decode on any antenna with any SDR" goal. Built on top of [[discone-vhf-hi-atsc-works]] (discone+port-C decodes VHF-hi ATSC).

**Files:**
- `sdr_caps.py` — detects ANY SoapySDR device, normalizes it. Reports antennas, freq range, max sample rate, gain elements, notch/bias-T capabilities, and the gain model (SDRplay's IFGR is INVERTED: higher=less gain). `detect_first_sdr()` picks the best TV-capable driver. This is the "any SDR" seed — on an RTL-SDR it reports a single dB gain + no notches and the pipeline adapts. GOTCHA: SoapySDR.Device() wants a "driver=X,serial=Y" STRING, not a dict, and NOT the 'label' key from enumerate().
- `antenna_profile.py` — sweeps the band, classifies interferers (in-band/out-of-band/out-of-sr), recommends hw notches (auto-EXCLUDES DAB notch when target is VHF-hi US TV since it overlaps), designs a FIR pre-conditioner, saves JSON profile.
- `auto_tune.py` — A/B tests 5 chain configs live, scores via FPLL telemetry (mean|x|, max|x|, in_rms, OsO-overflow), picks winner, writes to profile. WINNER on discone+C+RF7 = `long EQ + RFNOTCH + soft Viterbi` (pilot_dd/multifs/pilot_dd_soft all OsO'd = too CPU-heavy; SDR_AGC tanked in_rms to 51).
- `play_marginal.py` — marginal-signal player. LIVE 3-stage pipe: tail(live.ts, 188-byte aligned, follows growth) -> ffmpeg(-map 0:p:N isolates ONE program) -> mpv(error_concealment=3, fast probe). Plays without freezing.
- `auto_tv.py` — THE ORCHESTRATOR. detect SDR -> auto-pick antenna -> scan/force-probe -> tune -> play. One command.

**The "any antenna" smarts (auto_tv pick_best_antenna):** measures the 6 MHz ATSC power SHELF (central 6 MHz vs guard bands, DC spur masked) on EACH antenna port, picks the strongest. Discone-on-C reads +11.7 dB shelf vs empty ports A/B at +2 dB. Plug a TV antenna into any port -> it finds it. The naive peak-to-floor metric does NOT work (SDR spurs read ~22 dB on every port) — must use the in-band-shelf method.

**The marginal-signal playback recipe (what makes a weak signal watchable):**
1. Chain: `STVT_RFNOTCH=1` (frees ADC dynamic range from FM band: in_rms 269->354, +31%) + `STVT_VITERBI=soft` + `STVT_EQ=long` + `STVT_RS=erasure STVT_RS_ERASURES=20` (max RS erasure budget recovers most packets). Erasures=20 vs 14: less datamosh, occasional freeze (max budget can't always correct a deep-fade packet).
2. Player: isolate a LOW-RES SD subchannel via ffmpeg `-map 0:p:N` (mpv's own program_number is IGNORED through a stdin pipe — ffmpeg demux is the only reliable program selector). SD 720x480 I-frames survive packet loss; HD 1080i/720p60 I-frames are too big and freeze. auto_tv.pick_robust_program() picks lowest-resolution program automatically.
3. mpv: error_concealment=3 + video-sync=desync + cache-pause=no + audio-stream-silence=yes. Concealment keeps motion through loss (the "datamosh" smear IS concealment working — its amount = the packet-loss rate).
4. ANTI-FREEZE policy (the fix for "it froze"): freeze-vs-datamosh is a DECODER POLICY choice, not a signal fact. Freeze = decoder waits for a clean keyframe (shows nothing corrupt). Datamosh = decoder shows corrupt frames anyway (keeps moving). User prefers moving-glitchy over frozen-clean, so push toward always-show: (a) REMOVE `+discardcorrupt` from BOTH ffmpeg `-fflags` and mpv `--demuxer-lavf-o=fflags` so corrupt packets pass through instead of being dropped; (b) mpv `--vd-lavc-show-all=yes --vd-lavc-skipframe=none --vd-lavc-skipidct=none --framedrop=no`. GOTCHA: the mpv options are `--vd-lavc-skipframe`/`--vd-lavc-skipidct` (NO hyphen before frame/idct) — `--vd-lavc-skip-frame` is "option not found" and mpv refuses to start. This made it "play much better" 2026-06-23. Diagnosis that led here: chain lock was rock-solid (mean|x|=0.038, 0 lock drops) during freezes → freeze was 100% decoder-side missing-I-frames, not chain.

**Honest limit:** residual datamosh + rare freezes = the ~4-6% packet loss the discone-on-wrong-port can't avoid (vertical pol on HF port for a horizontal-pol VHF-hi signal). Every SOFTWARE lever is pulled. The actual cure is a horizontal-pol TV antenna on port A — the orchestrator would auto-detect it and run gap-free HD. The code is signal-limited, not capability-limited.

**2026-06-23 backyard field test — THE LIVE PLAYER IS THE WEAK LINK, NOT THE SIGNAL.** Tested 2 real TV antennas (shed omni on port A, directional on port B). BOTH auto-detected correctly via the in-band-shelf metric and BOTH produced clean TS: 7 services, 0 transport errors, RF36 WTTG Fox 5 DC + RF31/9/7/35 strong. Directional locked even tighter (mean|x|=0.013, best ever). DECISIVE PROOF the signal is fine: copied live.ts to a static file and played it → FLAWLESS (1 macroblock error in 8 min, perfect A/V sync). The SAME data glitches/freezes ONLY through the live tail-pipe → the bug is my live playback feed (mpv cache underruns on the hand-rolled tail thread), NOT the signal. Player lessons learned: (1) ffmpeg `-map 0:p:N` program isolation gives "Invalid frame dimensions 0x0" + mpv exit on this chain — DON'T use it; tail straight to mpv and let it auto-pick the program. (2) `+discardcorrupt` drops the sequence-header packets the probe needs → 0x0 dims; never discard on a clean signal. (3) the anti-freeze `--vd-lavc-show-all=yes` causes "frozen green" (pre-keyframe buffer) on a STRONG signal — it's marginal-only. (4) GAIN MATTERS PER PORT: antenna B needed IFGR=25 (in_rms 35→172, 0 services→7); IFGR=40 underran, IFGR=20 clipped (max|x|=1.57). The clean-lock sweet spot was IFGR=25-33 depending on port. (5) low in_rms with tight mean|x| = under-gain (gain scaling), NOT bad signal — boost gain, don't assume cable loss. **2026-06-23 KEY PARADOX — discone (VHF-hi RF7) gave MORE WATCHABLE TV than the real TV antennas (UHF RF31/36), despite the discone being VERTICALLY polarized (wrong for horizontal-pol ATSC).** Counterintuitive but explainable: it's almost certainly FREQUENCY/MULTIPATH, not polarization. RF7 = 177 MHz (VHF-hi); RF31/36 = 567/605 MHz (UHF). UHF wavelengths (~50cm) bounce hard off the house, trees, ground → severe multipath that locks the carrier (strong pilot, tight mean|x|) but SCRAMBLES the data (0 TS or ~23% loss). VHF-hi wavelengths (~1.7m) are far more forgiving of multipath at a cluttered backyard location. So the discone's VHF-hi advantage beat the TV antennas' polarization+gain advantage AT THIS SPOT. Decode-rate evidence this session: discone RF7 played watchable SD; directional/shed on UHF RF31 = 0 decode (multipath), RF36 = marginal ~1850 KB/s both antennas. LESSON: at a multipath-heavy ground-level location, prefer the LOWEST usable RF channel (VHF-hi RF7-13) over UHF, regardless of antenna type — and judge by DECODE RATE (live.ts growth / decode_meter.py), never by pilot SNR or power-shelf (both peak on multipath reflections). USER'S NEXT IDEA (good): try an antenna on the OTHER SIDE OF THE HOUSE — different line-of-sight to the DC towers, likely less multipath. Also worth: height (get above the roofline / ground clutter) and favor VHF-hi channels. The universal code (auto_tv.py) will auto-detect whatever antenna/port and the decode_meter shows the truth — re-run from the new location.

**2026-06-26 — THE "GARBAGE ON A STRONG ANTENNA" BUG (root cause of half the field-test pain) + adaptive gain fix.** User moved the real attic TV antenna to ANT-A (it "worked great on the old code") and asked the new code to decode it. First attempt with the universal play path FAILED — but in a sneaky way: live.ts grew at full ATSC rate (2.8 MB/s) yet was FULL-RATE GARBAGE. Proof: 0 MPEG-2 sequence headers (00 00 01 B3), 0 PES start codes, 0 PAT (PID 0), 0 PSIP (PID 0x1FFB), and a COMPLETELY DIFFERENT random PID set in every 30-60 MB window (real ATSC has a stable handful of PIDs). tsanalyze even showed "0 transport errors / 0 invalid sync" (TEISCRUB hides it) so the file LOOKED healthy. ROOT CAUSE: the play path hardcoded `STVT_IFGR=30` — a HIGH-gain marginal-signal setting (IFGR is INVERTED: lower=more gain). On a strong attic signal that OVERDROVE the ADC into clipping → carrier locks (FPLL fine) but the 8-VSB slices are wrong → RS can't correct → full-rate noise dressed as TS. FIX: the scanner's proven `CHAIN_DEFAULTS` use `STVT_IFGR=45 STVT_RFGAIN_SEL=3 STVT_RS=stock` (+ SPS=1.1, RRC_SYMS=8, TEISCRUB=1, EQ_LKG=1). Switching to IFGR=45 gave INSTANT clean decode: 54 seq-headers + 1957 picture-starts + 407 PSI packets / 25 MB, AC-3 5.1 audio, 4 strong DC UHF locks (RF21 WDCW, RF31 WPXW, RF34 WRC NBC-4, RF36 WTTG Fox-5). WRC NBC-4 HD 1920x1080 played live, gap-free, 2395 KB/s.
  TWO KEY LESSONS baked into auto_tv.py this session: (1) **FILE GROWTH ≠ DECODE.** Garbage streams at full rate too. The only reliable "is it really decoding?" test is counting MPEG-2 sequence-header start codes (00 00 01 B3) in the live.ts tail — added `count_video_starts()` / `has_real_decode()`. The old `locked = live.ts > 10MB` check passed on pure garbage. (2) **GAIN MUST ADAPT TO THE ANTENNA, not be hardcoded.** Added `calibrate_chain()` + `GAIN_LADDER` (strongest→weakest: IFGR 45,50,40,55,35,30,25) that walks gain until `has_real_decode()` passes — so ONE code path covers a strong attic antenna (needs IFGR~45) AND a weak discone (needs IFGR~30) automatically. `auto_tv.py` now: calibrate gain (default) → validate real decode → play; `--deep` adds the old A/B auto-tune; `--quick` uses cached/defaults. The IFGR=30/erasure-RS marginal recipe is NO LONGER the default (it was tuned for the discone-on-wrong-port and actively breaks strong antennas). Also: this PSI-starvation likely explains part of the old "live player bug" — ffmpeg `-map 0:p:N` emits nothing (aq=0 vq=0) until PSI appears in its input, and garbage/PSI-sparse output starved it; clean decode has PSI repeating ~every 60 KB so the live tail-pipe now works (verified: 119 HD frames from an 8s live-pipe test, then sustained live playback).

**2026-06-26 part 3 — the AUTOBOT TEST APPARATUS (ported from Linux) + the long-USB/common-mode overload diagnosis.** User reported the ANT-A picture glitching (motion blocks + audio cutouts) despite a clean RF lock, and asked for the "test apparatus that analyzes every aspect of the video at once" (the Linux `quality_judge.sh`). Ported it + built a suite in `Z:\src\adaptive-tv\`:
  - `quality_judge.py` — Windows port of quality_judge.sh: snapshots live.ts tail, ffmpeg null-decodes the program's video+audio, counts frames→fps + video decode errors (ac-tex damaged/MVs not available/concealing) + audio errors, scores 0-100 (cable_quality 90+ / watchable 60+ / glitchy 30+ / broken). Writes %TEMP%\quality_state.json. THE objective "is it glitchy" oracle — no more asking the user.
  - `quality_sweep.py` — A/Bs chain configs (gain × RS mode), scoring each with quality_judge, ranks them, leaves chain on the winner. CAVEAT learned: single 12s windows are unreliable when the signal is fluctuating (see below) — its "winner" was a lucky window; use the stress test for unstable signals.
  - `stress_test.py` — runs the chain for N min, every cycle logs quality_judge score AND parses chain telemetry (mean|x|, max|x|, in_rms, peak-clip/disturbance count, overflow count), correlates, and prints a time-series + diagnosis (steady-marginal / intermittent-fade / bursty-overflow). THE tool for characterizing flaky playback over time.
  - `player_probe.py` — measures the PLAYER feed specifically (tail→ffmpeg demux, ±discardcorrupt) to separate chain-vs-player.
  - `play_live.py` — buffered VLC live player (no +discardcorrupt, fat cache, starts N s behind edge) — fixes the freeze/skip of the mpv-pipe players for a CLEAN signal.
  DIAGNOSIS REACHED (apparatus did it, not the user's eyes): quality_judge showed the CHAIN output itself was glitchy (15-43 video err/s), so it was NOT the player. stress_test (4 min, 56 samples) showed score swinging wildly 26→80 (avg 48) with mean|x| rock-steady clean (0.033) but frequent max|x| disturbance spikes to 1.57 every few seconds — AND in_rms stuck at ~185, vs ~50 this morning when it "played great". A hard gain-cut test (IFGR=59 min IF + RFGAIN_SEL=0 min RF) only dropped in_rms 185→162 and made decode WORSE (score 0) — PROVING the high input energy is NOT from gain settings; it's a strong signal/interferer/noise sitting at the antenna input that software can't attenuate. FIRST (WRONG) THEORY: common-mode loop from the long USB cable. REFUTED — user switched to a short cable and in_rms stayed ~199, max|x| still railing. ACTUAL ROOT CAUSE (found by spectrum sweep): **FM BROADCAST OVERLOAD on ANT-A.** Per-port raw-IQ check localized it — ANT-A read 10x the level of B/C (RMS 0.149 vs 0.014 vs 0.006); a coarse spectrum sweep on ANT-A showed the FM band (98 MHz) DOMINANT at -6.3 dB, ~10 dB STRONGER than the wanted ATSC at 593 MHz (-16.7), plus a strong 150 MHz. The big attic antenna grabs huge FM, saturating the RSPdx wideband front end → FPLL phase detector RAILS at max|x|=π/2 (1.5707) → 0 decode, even though mean|x| pilot looks ok. THE FIX (software, recovered it to watchable): enable BOTH hardware notches `STVT_RFNOTCH=1` (FM/AM) + `STVT_DABNOTCH=1` (174-240 MHz VHF) AND back off RF gain for front-end headroom: `STVT_RFGAIN_SEL=2 STVT_IFGR=42`. Result: video errors 21-43/s -> 2-3/s, score 0 -> 78 (watchable), max|x| π/2 -> 0.26 (FPLL stable). KEY LESSON: max|x| RAILING at π/2 (≈1.5707) + a strong out-of-band signal in a spectrum sweep = FRONT-END OVERLOAD by an interferer (usually FM on a big/wideband antenna); cure = hardware notch(es) + REDUCE RF GAIN (rfgain_sel), NOT more gain and NOT a cable change. Diagnostic recipe that nailed it: per-port raw-IQ RMS to localize, then a coarse spectrum sweep on the hot port to identify the interferer. KEY TELEMETRY LESSON: in_rms ~4x normal + min-gain can't reduce it = front-end overload/common-mode, NOT a gain knob problem; and max|x| is the FPLL ERROR (disturbance), not ADC level — frequent max|x|→1.5 spikes with clean mean|x| = intermittent interference corrupting DATA while the PILOT survives (so RF "looks locked" but picture glitches).
